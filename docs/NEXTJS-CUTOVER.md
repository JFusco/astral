# Next.js cutover verification

Verified locally on October 25, 2026 against the working tree. The frontend used
Next.js 16.4.3, React 19.3.1, Motion 14.6.0, Tailwind 4.3.3 and Three.js 0.186.1.
Node 24.14.0 and the existing Python 3.13 virtual environment were used.

On October 26, Health adopted Overview's shared orbital renderer and removed
Three.js; see [HEALTH-ENGINE.md](HEALTH-ENGINE.md). The results below retain the
original cutover evidence.

## Result

The sole frontend is `frontend/`, with App Router routes `/`, `/health`,
`/accounting` and `/learning`. The static `dist/` frontend and its shell/font-copy
build scripts were removed. Python serves APIs only. The local production frontend
started at http://127.0.0.1:3000 and returned HTTP 200 with the rendered Overview
frame and navigation. The old boot script was absent.

an escalated attempt. The successful build result applies to Webpack.

## Browser and service evidence

Playwright used installed Chrome, production standalone output, owned ports
18730/18766 and a temporary simulator ledger. Only this isolated simulator enabled
orders. Health fixtures and saved reports were test evidence, not provider proof.
The saved reports were generated by the actual Python offline evaluators from a
separate empty temporary source ledger. All test processes shut down after the run.

The eight cases verified:

1. Direct loads and navigation across all four screens, three repeated navigation
   cycles, a functioning Three.js view, one retained event stream, bounded
   animation-frame ownership, no page errors and a 404 for a legacy HTML route.
2. A delayed initial response, visible loading UI, zero infinite loading animations
   under reduced motion, a narrow viewport without horizontal overflow, display
   settings and Escape dismissal.
3. One simulator buy despite a lost response, submission blocking across
   navigation until explicit reconciliation, halt/resume, then an actual simulated
   sell. Both distinct intents were submitted once; stored orders, a sell fill and
   lower position quantity were verified through the relay.
4. Exact API paths, no-store responses, invalid-host rejection, missing-intent
   rejection, foreign-origin rejection and successful legitimate same-origin writes.
5. Actual SSE replay via Last-Event-ID despite a conflicting query cursor, plus
   order cancellation through the relay to the simulator.
6. Actual saved-report compatibility, unknown money results, retained stale figures,
   protected-window metadata, immediate abort on navigation during manual refresh,
   successful return to Accounting and no POST caused by report refresh.
7. Rejection of malformed state without displaying its invented balance, an honest
   unavailable state and recovery to real simulator readback.
8. Live application motion changes stop and resume Health meteors on the identical
   WebGL canvas, with no context loss/restoration, fallback status or page error.

## Adversarial review and repairs

Claude independently reviewed the scoped migration source with the user's explicit
source-export authorization. Six accepted source defects were repaired: the Docker
build's missing standalone-script copy, Health renderer recreation on motion changes,
unknown-symbol fill effects crashing the overview animation, nullable optional news
metadata rejecting dashboard state, older HTTP state overwriting newer SSE state,
and manual report refresh requests surviving unmount.

The first browser run after repair exposed a test race: the final Accounting checks
could match the outgoing Learning page. That failure was retained; the follow-up
waits for Accounting-specific content and its fourth GET. It also adds live Health
motion coverage and actual sell readback. The final Chrome run passed all eight
cases in 40.2 seconds. Independent review checked the full JSON outcomes and source
hash, and final verification completed with no findings.

Review lineage: source repair `f26cfd5d-627d-42af-9210-81db074f5bcc`, browser follow-up
`01f4e099-32b3-44a4-afdc-6fa45cf9ad54`, completed evidence verification
`ee805a31-c157-46bb-9779-c3e23efcbc7f`. Earlier runs retain their unresolved status
where browser evidence had not reached their frozen packets. The final verification
explicitly checked the later evidence; historical failures were not relabeled.

The final browser test source SHA256 is
`ace2061b9fc2b55a1f66f83736bc1a64e51e3d8276108e8fb5050b78e9f7c38d`.
These are local simulator and fixture results. Docker image/runtime, private-account,
broker and real provider-health acceptance remain outside this result.

Screenshots/traces are ignored under `frontend/test-results/`. The desktop and
mobile loading screenshots were visually inspected. Browser acceptance establishes
these local UI/service behaviors; it does not establish broker execution, provider
freshness, remote availability or trading readiness.

The relay's transport matters: a local probe showed Node Fetch replacing a supplied
Host with the upstream authority. The final relay uses Node HTTP to preserve the
validated browser Host and Origin, and the production same-origin tests passed.
FastAPI's origin/intent enforcement remains active. Invalid upstream/configuration
or transport failures never cause automatic mutation retries.

The generated client assets were checked for broker credential-variable names,
private-ledger paths and private receipt markers; none were present. Fonts are
bundled locally; retained Fontsource and Three.js notices are under
`frontend/public/licenses/`. The deterministic risk, broker, engine, store and frozen
experiment files have no changes in this cutover. Existing Python processes,
credentials and execution flags were not restarted or modified.

The current official [useReducedMotion reference](https://motion.dev/docs/react-use-reduced-motion)
promises live device-preference updates. Independent inspection found that the
installed hook initializes state without a reactive setter subscription. This is a
version-specific documentation gap, not a completed browser reproduction of OS
preference changes. The verified live test changes the application's reactive
storage/custom-event setting; an OS preference toggle remains a separate check.

These captures are saved reference/lesson records, not published Brain guidance or
mirrors of entire vendor documents. See the frontend README for official source links.

available in this checkout and it is not part of the new frontend.
